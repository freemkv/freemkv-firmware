# MediaTek PREPARE signature audit (WH16NS58 1.V9)

Status: no firmware-code predicate currently authorizes ignoring a failed
PREPARE in normal Flash. This note records static evidence, not a hardware
validation or a change to the flashing policy.

## Observed failure

The 0.14.1 Windows attempt sent one zero-payload WRITE BUFFER PREPARE
(`3B 01 00 00 00 00 00 00 00 0B 00 00`, ToDevice). The transport reported
CHECK CONDITION (`02`) with a parsed `00/00/00` sense triple. No STREAM
command or firmware payload followed. The installed receiver's update-mode
state after PREPARE was not established. A selected current-firmware file
matched live identity and a small metadata window, but protected READ BUFFER
access prevented a live code match.

The Windows libfreemkv 1.8.2 transport passes a fixed 32-byte sense buffer to
the parser instead of the returned `SenseInfoLength`. Thus `00/00/00` does not
prove that a valid NO SENSE response was supplied. Its zero-length ToDevice
buffer pointer is null; the signed 1.V9 OEM transport supplies a non-null
pointer. Neither difference has been physically isolated as the cause.

The signed 1.V9 updater *sends* PREPARE once per round; it does not omit it.
Its shared loop does not branch on the PREPARE result, but aborts on a failed
STREAM. The WH16NS58 1.V7 updater uses the same plain-01 PREPARE dialect and
checks its result in both rounds.

Seven of these packages bundle the **exact same** intermediate image
(`c3a18eed17251d1508964647e833ffdfe01b13c28dff9a717dfac6336e7c70e6`):
the signed 1.V9 package and six checked-updater packages (WH16NS58 1.V7,
WH14NS40-NS50 1.05, BH16NS55 1.05 packages, BH16NS40 1.05, and WH16NS40
1.05). Consequently, no function of that intermediate image's bytes alone
can reproduce the OEM programs' opposite second-round policies. This does
not prove either policy safe for a failed live command.

The broader executable scan screened 142 PE files: 86 binaries had a
recognized PREPARE signature, with 102 located callers that checked the
return. Another 56 files were unmatched and are **not** classified as lacking
PREPARE or as checking it. The signed Vinpower inner DLLs were recovered and
audited separately. These figures are corpus coverage, not a population-wide
frequency claim.

## Firmware-code comparison

The published WH16NS58 1.V7 final image is SHA-256
`569cea9bb8add8b5638fbf0f5ea47b8014f851f007b2cbef2be44737d7cdbf68`;
the 1.V9 OEM reference is
`97b287072e20c9527de6f34f6d564c8edcc6afb3ecf5675c11b8262c11663061`.
Direct byte comparison finds:

| Code | 1.V7 file offset | 1.V9 file offset | Result |
| --- | ---: | ---: | --- |
| Mode/buffer guard | `0x9c04a`, 38 bytes | `0x9c046`, 38 bytes | identical |
| PREPARE mode-one flag-setting body | `0x9d116`, 66 bytes | `0x9d112`, 66 bytes | identical |

The four-byte offset shift is a relocation of surrounding code, not a
semantic difference in these two windows. The BOOT completion *shape* of the
1.V9 image is shared by 107 images in the local static census, including
checked-updater pairings. These limited windows do not prove that the whole
application dispatch, asynchronous completion, or live receiver is identical.
They do rule out either window as a 1.V9-only permissive signature.

## Safe decision boundary

Do not classify `CHECK CONDITION/00/00/00`, a version string, target-file
hash, selected current-firmware file, or the shared entry-body bytes as
permission to stream. An evidence-based rule would first need (1) raw Windows
SCSI status, returned sense length/response code and buffer-pointer behavior;
(2) a verified binding to the installed receiver code or a receiver-state
probe after exactly one PREPARE; and (3) a hardware trace demonstrating that
the resulting state accepts the intended STREAM and completes safely.
Transport failure, timeout, invalid sense, or unrecognized receiver state
remain stop conditions. STREAM errors stay strict, without automatic retry.

The protocol layer should report typed facts: entry attempted with zero
payload, payload command attempted, acknowledged bytes, upload complete, and
startup/readback verdict. The flasher should compose those facts with
multi-stage/temporary-firmware context and render localized guidance. A
PREPARE failure is neither proof that firmware was written nor proof that the
drive was unchanged.
