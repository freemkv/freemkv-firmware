# Independent authentication cross-review, 2026-10-30

Verdict: the assertion that the existing AKE/encryption hooks establish that G07/G08 are unnecessary for UHD sector reads is **unproven**. They do not implement native AACS2 host authentication; they may support a narrower raw-read workflow when encryption is explicitly Off. The currently inspected evidence does not establish that workflow succeeds end to end, or that every READ command reaches its data phase, on any converted older image. Thus diagnostic-only treatment is a product-scope decision, not a demonstrated equivalence to native UHD authentication or a proven raw-read guarantee. No physical drive was exercised.

`engine/mt1959_uhd.rs` plans G01–G06 and records G07/G08 without blocking or patching. `engine/mt1959.rs` installs the separate AKE reject-writer/shared-call hook, VID producer compare hook, and deny reset. `engine/core.rs::build_gatea_stub` explicitly identifies its gate as READ DISC STRUCTURE 0xAD format 0x80, not READ(10)/(12)/(16): Encryption Off invokes session reset, clears AGID structure bits 0xc0, and goes to the VID-producing continuation; On and Passthrough reproduce the auth-byte == 6 check. The AKE stub's Off case accepts a rejected certificate; On and Passthrough retain the OEM outcome. These controls do not add the extended-mode workers or response buffers. The default is Encryption Passthrough (ABI boot defaults), so the Off branch cannot be presumed on a default configuration. UHD Off additionally forces its existing REPORT KEY class gate to refuse, while On and Passthrough replay native behavior.

Independent interpretation of source-bound existing CPU receipts (not a new hardware run): for BU40N 1.02 SHA-256 `1bbeb5351dc0d69feaeefdac9ada7f3f48eed0ca4e2f879d9266679cec133396`, the registered 0xa4 format 0, media 0xc7 class 2 and 3 wrapper reaches call site 647926 -> 1271772; 0xa3 reaches 648038 -> 1271978. The harness intercepted the preliminary guard at 647934 or 648004 -> 1300482 and supplied return 1; it did not execute the crypto exchange. At 1271772 the mode/class worker selects class 3 only in mode 1, and mode 0/class 3 reaches sense call 1271842 -> 665966 with (5, 0x6f, 1). Certificate worker 1267788 has mode-selected 116/180-byte lengths. The extended auth operation 0xb3 calls 1268080 -> 828772; the latter calls kernel service 828780 -> 724. This is native session machinery, not the VID gate.

For BN11 SHA-256 `5c01c1fda59f3db130bd14aa64fe97d4010376798716b16792dbffd59c488a95`, the same wrapper test reaches 646058 -> 1265808 for 0xa4 and 646288 -> 1266014 for 0xa3, after guard intercepts 646066 or 646248 -> 1295534 returning 1. Its worker reaches sense call 1265878 -> 664094 for mode 0/class 3; mode 1/class 3 dispatches normally. Certificate entry 1261824 also has the 116/180 mode-dependent response. BN11 is therefore not a legacy-auth counterexample: although it lacks several media selectors, it already has the tested class routing and extended worker. The receipt data are `mt1959-uhd-keys-receipts-20261030.json`, `mt1959-uhd-key-worker-receipts-20261030.json`, and `mt1959-uhd-auth-service-receipts-20261030.json`; addresses above are decimal image offsets, exactly as recorded.

A real counterexample to the universal claim would require tracing an image with actual G07/G08 gaps from registered READ command through all media/auth checks to optical data transfer, both before and after the emitted Off hooks, and observing response/data buffers; conversely the absence of class-3 host-auth parity alone does not prove that a raw sector command fails. Establish separately: READ command opcode registration and dispatcher, state and gate inputs, both continuation targets, encryption latch and response lengths, and content bytes. Test Off, On, and Passthrough and distinguish raw AACS-encrypted sectors from playable decrypted content. Existing wrapper/worker receipts stop at explicitly intercepted calls and cannot stand in for these downstream observations. This review did not complete that trace or test the 1.V9 fixture; it must not be represented as a positive end-to-end acceptance result.

## 1.V9 READ dispatch follow-up

For WH16NS58 1.V9 SHA-256 `97b287072e20c9527de6f34f6d564c8edcc6afb3ecf5675c11b8262c11663061` (G07/G08 gaps), direct Thumb disassembly in `/tmp/freemkv-auth-terra-read.py` shows that the 0x28 READ(10) record at 0x156454 and the 0xa8 READ(12) record at 0x15645c have flags 2 and a null handler. The native scanner at 0x18680 matches them; flags 2 invokes readiness checker 0x143cb2 at 0x186fe with r0=1. The checker has independent sense/refusal exits, including 0x143d72–0x143d92 to sense 0xa314a, and its success exit 0x143d9c–0x143da6. On success scanner 0x18740 checks the null handler and returns the matched record. Caller 0x1843e copies the record at 0x18448–0x18462 to RAM at 0x02000d14 and advances a queue index at 0x02000cf0. This proves a distinct readiness/queuing stage, not optical sector transfer. Static disassembly has not established the asynchronous queue consumer or actual Off/Passthrough outcome, nor executed patched bytes. No conclusion on raw sector acceptance can be drawn from this partial path.

BN11 clarification: the exact hash above has G07/G08 `reviewed match` in `mt1959-uhd-gap-table-20261030.json`; its conversion plan records an empty authentication difference list. The matched 30/30 class-routing cases are wrapper-to-first-worker tests, not full session authentication. That scoped observation does not establish functional AACS2 playback or physical sector reads.

## Local product command profile

Local source inspected: `freemkv-unlock` commit `c8f84313fb3fc5dea329b5a20e68342fa9621ad8` (clean) and `libfreemkv` commit `e30b3afe29e80388da626c64884508fd43996d10` (only Cargo.lock modified). This narrows the previous verdict: **G07/G08 can be excluded from the host command profile of a successfully activated freemkv firmware unlock**, because that route does not request the native class-3 handshake or its extended certificate response. This is not evidence of optical transfer, native AACS2 parity, or operation for an arbitrary host.

`freemkv-unlock/src/freemkv/mod.rs::activate` attempts Region, Speed and Unrestricted=On when advertised, tolerating non-transport failures for these optional SETs. It requires the Encryption=Off SET to return success; this path does not GET/read back the flag. After backend verification, `get_vid` issues bare READ DISC STRUCTURE 0xAD, format 0x80, AGID 0, allocation 36 (`src/vid.rs`). A VID refusal/short response is nonfatal. For a preinstalled backend `verify` uses the default no-op. The client's success means the SET was accepted, not that physical UHD data was read. Separately named `FirmwareControl` recipes use set-and-verify, but are not this activation path.

`libfreemkv/src/drive/mod.rs::init` calls the firmware unlockers, records the successful unlocker and optional VID. `disc/encrypt.rs::do_handshake_cert` explicitly skips the host-certificate handshake both when a VID was stashed and when firmware claimed the drive without one. The sector reader `drive/mod.rs::read_one` sends READ(10) 0x28 and expects a full `count * 2048` transfer. This sequencing is source evidence for the host path, not a bus capture or proof all hardware/state interactions succeed. If firmware unlock is not claimed or SET fails, the client can take the distinct AACS host-certificate route (`unlock_bridge::run_bus`), whose A3/A4 builders currently use key class 2 even in its P-256 code; do not describe this as proven native class-3 host operation. A non-freemkv host or enabled/OEM encryption can need different functionality.

On the firmware side the Off VID gate calls the native AACS reset then continues at the native producer's authenticated branch; the source binds the native per-AGID state setter from `movs r1,#1; bl` sites in that producer and reset. That local relation does not demonstrate a data dependency from the setter to 1.V9's 0x143cb2 READ readiness gate or the subsequent queue consumer. Establishing that dependency, exact patch-byte execution, and a real data transfer remain open. In particular, SET accepted plus no host class-3 requests does not prove that the mechanism bypasses every drive-side read gate or removes in-transit encryption under all conditions.
