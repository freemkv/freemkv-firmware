# Flash and Recovery path audit

2026-10-21. Scope: GUI, CLI/shared workflow, backend preparation, transport,
receiver-owned execution and completion. Reviewed the pinned MediaTek
`3660c1c556f450bc17f7a2cea8b6e787f82c77e7` and Pioneer
`f67a7bd5e73fce83f418af9dc6732c4f99922c7c` dependencies, rather than assuming
similarly named public entry points imply separate writers.

## Conclusion

Flash and Recovery already share each protocol's low-level writer and verifier.
Separate policy/preparation entry points are appropriate. A separate chunk writer,
encoding implementation, commit loop or success criterion is not needed.

For the same running application and target, the new command-transcript tests
prove byte-for-byte identical data-out commands and payloads on both MediaTek
and Pioneer. Recovery's loader handling and entry-error tolerance belong to the
existing shared executor's recovery mode, not an alternative transport.

## Trace

| Layer | Flash | Recovery | Assessment |
| --- | --- | --- | --- |
| Desktop input | Current source and target | Same shared form | Both now default to drive reads; paired Current choices remain explicit |
| Host policy | Backup, coverage/model/family checks, consent and tray checks | Explicit recovery consent; no automatic backup or normal Flash policy | Deliberate difference |
| MediaTek receiver | Live detection or explicitly bound Current file | Same two evidence sources | Fixed inconsistent file selection; reference revalidation remains mandatory |
| MediaTek wire plan | `receiver::TransferPlan` | `recovery::PreparedRecovery` contains `receiver::TransferPlan` | Same receiver-derived PREPARE and header/body encoding |
| MediaTek executor | `TransferPlan::execute_completed` | Same method after banner recheck | Same stream, commit, readiness, protected readback and exact target-startup completion |
| MediaTek entry | Descriptor probe, readiness, PREPARE; any failure stops | PREPARE without normal probe/readiness; one failed PREPARE is reported and streaming continues once | Existing explicit recovery policy; no retry or guessed CDB introduced |
| Pioneer executor | `flash::execute_prepared` and optical `PreparedUpdate::execute` | Same functions with `ExecutionMode::Recovery` | Same migration, transfer, restoration and verification machinery |
| Pioneer loader | Normal running receiver required | A positively identified loader can resume without normal application entry/parameter commands | Required to recover a loader; subsequent restoration uses the normal verified path |
| Completion | Shared structured verification quality and startup evidence | Same | Recovery does not convert unreadable bytes or a mismatching target into full verification |

The engine's Recovery wrapper skips the generic tray gate. Pioneer still checks
the tray through the shared execution runtime before each pass. MediaTek retains
chip, image integrity and receiver-contract checks. Pioneer retains hardware-family,
integrity, programmer/dialect and handoff checks. The shared warning now says
"some compatibility checks" rather than implying all checks are removed.

## Reproduced and fixed

1. Recovery did not default to drive reads, unlike Flash. Both desktop forms now
   use one presentation builder, the same input ordering, selectors, paired
   Current-member controls and Check file action. Recovery's warning and single
   target-member choice remain specific to that operation. Normal Flash backend
   capabilities still determine whether an explicit Current file is supported.
2. MediaTek Recovery silently preferred readable live code over a selected Current
   file. A mismatching selected revision returned `Planned` before the fix. The
   new regression test now requires rejection before any write; explicit file mode
   always analyzes and binds the file to the live receiver's identity/build data.
3. Recovery's GUI could reuse a stale selected file/member despite drive-read mode
   on a backend accepting an optional reference. Drive-read mode now consistently
   sends `ReadFromDrive` and no Current member. The selected mode/inputs remain
   frozen through preview and confirmation.
4. Automatic MediaTek recovery receiver-read failures exposed a long protocol
   diagnostic. They now use the same concise Current-file guidance as Flash while
   the original error chain and read counts remain in diagnostic logs.
5. Matching the forms exposed a clipped Flash action row in the egui fallback.
   Both forms now receive the same sufficient form height. The small-window render
   test checks visible controls; native macOS's GUI gate passes 110 checks.

## Existing target constraints

The CLI/shared Recovery workflow accepts TAR targets only. MediaTek selects one
declared image from a paired TAR and never automatically follows its other stage.
Pioneer Recovery requires the Kernel+Normal pair needed to restore its receiver;
ordinary Flash additionally supports Normal-only input. These existing input
constraints were audited and preserved; no new BIN Recovery feature was added.
The desktop defaults do not change the CLI's explicit source options.

## Test evidence

- UI alignment test failed before the default/layout change and passes afterwards.
- Selected-Current regression failed before the source-selection fix and passes
  afterwards, with no writes on a stale reference.
- MediaTek and Pioneer normal-application Flash/Recovery write transcripts match.
- A rejected MediaTek PREPARE stops Flash before streaming, while Recovery makes
  exactly one attempt and preserves its existing continue/verify behavior.
- Existing tests retain loader handling, temporary/pristine Kernel restoration,
  unsupported-programmer refusal, byte mismatch and incomplete-verification behavior.
- All seven published BU40N 1.00 TARs pass Modify and simulated Flash as TAR/BIN
  on both 0.13.4 and 0.14.0. Source packages were retrieved from the production
  site's archive and checked against all published package hashes.

Physical flashing remains unperformed. Final QA still must pass the optimized
cross-platform tests, native gates and full package matrix for the exact candidate.
