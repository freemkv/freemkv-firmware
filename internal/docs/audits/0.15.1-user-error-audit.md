# 0.15.1 user error and guidance audit

Audit date: 2026-10-24. Scope: the shared `freemkv-flash::UserError` classifier, both optical backends, flash and recovery workflows, CLI output, Flash GUI, Modify GUI, and every embedded user-facing error catalog. This is a source and test audit; it does not claim physical-drive testing or native-speaker review of all translations.

## Follow-up: nested error and consequence audit

This section corrects an overstatement in the earlier audit below. The earlier review compared stable error IDs and checked backend source paths, but it did not test every nested cause through the outer `UpdateFailure` wrapper into the final CLI/GUI message. The report `freemkv-report-9dead7be-9b88-4041-86f0-abdd59ca86bf.zip` is from app version 0.14.5. It records a Pioneer A0 startup-setting write/rollback failure, with no firmware update-entry command or payload in the log. It does not prove a 0.15.1 producer failure.

The immutable 0.15.1 source was checked directly: Pioneer `execution_error` sets the update progress to `Preflight` when `ExecutionError::firmware_write_started()` is false. It stores the legacy `write_started` flag separately, because an A0 setting mutation is not a firmware update command. The nested Pioneer startup rollback issue is attached as `StartupSettingUncertain`, and a blocked failure reaches the specific issue branch in `UserError`. The production source therefore does not classify this particular startup-setting boundary as `EntryAttempted`. The 0.14.5 event string is inconsistent with the protocol boundary shown by its attached log evidence; the new regression below is built from the current producer and synthetic outer-wrapper conflicts, rather than treating the old report as a current-version repro.

| Concrete failure boundary | Producer evidence | Outer wrapper and classifier result | User-facing disposition and coverage |
|---|---|---|---|
| Target/current validation, device selection, backup destination/required backup, compatibility, or settings conversion rejected before execution | Typed `IssueCode`, `CorruptFirmware`, compatibility mismatch, or settings error; no update command | `UpdateFailure::before_write` or `NoFirmwareWrite`; cause ID stays specific and consequence says no firmware write where valid | Action identifies the file, drive, backup, or prerequisite. Existing gate, engine, recovery, and localization tests cover specific cause + consequence. |

Covered through `migration::execute` → production `execution_error` → `workflow::user_error` → localized render. |

| Legacy or contradictory outer wrapper says Pioneer startup-setting failure was `EntryAttempted` | Typed `StartupSettingUncertain` accompanies `UpdateFailure::EntryUncertain` | The typed startup cause wins; generic “drive asked to start an update” is suppressed because producer evidence identifies the earlier boundary | Red/green regression ensures a stale `write_started`-based outer classification cannot hide startup-setting cause or invent update mode. | Firmware payload command attempted, zero acknowledged bytes | Pioneer firmware writer error or MediaTek payload-write attempt evidence | `PayloadAttempted` → `errors.update_uncertain` | Says firmware may have been written; no immediate retry instruction. Pioneer and MediaTek recovery tests cover them; recovery-specific typed cause remains visible where it does not conflict with stronger write evidence. |
| Connection/revalidation or drive identity changes | Typed `Connection`, `DriveChanged`, receiver revalidation, SCSI sense, or backend unavailable evidence | Before write: specific connection/drive issue plus no-write. During/after write: update progress consequence remains primary | Before-write message asks to reconnect/reselect; after-write message keeps uncertainty and requests inspection. Platform, workflow, and backend stage tests cover both sides. |
| Corrupt/invalid target or incomplete/mismatched Current/backup | `CorruptFirmware`, `FirmwareInvalid`, `CurrentIncomplete`, `CurrentMismatch`, `BackupMismatch`, or typed backup errors | Cause is preserved over source-chain prose; no-write is added only at a write-prohibited boundary | Names the selected object and concrete remedy. Engine, Pioneer/MediaTek recovery, and backup tests assert IDs and the no-write consequence. |
| Read-only/Modify operation, cancellation, panic, worker disconnect | Operation capability, cancellation event, worker write capability, or captured active failure evidence | Read-only gets no-write; write-capable interrupted workers get blocked/uncertain based on recorded operation evidence; unknown state stays generic and conservative | Modify failures do not imply drive writes. Flash GUI interruption preserves active write evidence. Native shells share the encoded issue/render path. GUI worker and runtime issue tests cover these routes. |

This follow-up changes the Pioneer startup-setting messages in all 29 catalogs: the firmware update command and payload were not sent, while the drive’s startup setting may still have changed. `UserError` now gives this typed startup-setting cause precedence over a conflicting entry-only wrapper, suppresses the generic no-firmware-write consequence for that case, and still preserves payload uncertainty or temporary-firmware evidence when those stronger outcomes are present. The new regression cases are deliberately nested; they would fail if the outer wrapper again replaced a more specific startup cause or if startup wording hid actual payload uncertainty.

The English CLI and Flash GUI use the same `UserError::render` data. The current producer regression enters through `workflow::user_error`, the shared path used by both. Catalog rendering is checked for all supported languages; this validates key resolution and nonempty output, not native-speaker quality.

|---|---|---|

| `CurrentFirmwareRequired` | `errors.current_required` | Explains that installed firmware cannot be completely read/identified and requests matching Current firmware. |
| `BackupReadRestricted` | `errors.backup_restricted` | Explains this is expected for many MediaTek drives. |

Pioneer and MediaTek map their optical library's `IssueKind` values consistently: invalid/unsupported firmware, receiver mismatch, hardware mismatch, connection, verification/update uncertainty, and unexpected. Pioneer preparation distinguishes unresolved settings from unsupported intermediate-transfer flows and reports startup rollback outcomes separately. The issue classifiers preserve typed causes through `explain`; boundary context supplies a fallback only when no recognized cause exists.

## Specific findings and changes

1. The normal-only compatibility refusal had the required and installed Kernel tags in diagnostics, but user guidance reduced it to a generic installed-firmware mismatch. It now carries typed `{required}` and `{installed}` values through CLI and GUI localization. Component headers are validated independently before comparison, so malformed Current/target errors keep their own cause and the error is not produced for an incoming Kernel+Normal pair. A regression test covers ID72 versus GENERAL, invalid-current/target precedence, and a complete pair replacing the old Kernel.
2. The `errors.hardware_mismatch` English text was indirect, and several translations had malformed label punctuation/wording. The message now directly states that installed and selected firmware are for different hardware, labels both identities consistently, and tells users to choose firmware compatible with the drive; all 29 catalogs were updated.
3. The settings and required-backup messages now explain the prerequisite in everyday terms and give the next step. Other backup, unsupported-device/firmware, and recovery messages were reviewed against their producers; no lost typed causes or false write claims were found there.
4. This follow-up corrected nested startup-setting precedence and wording. The older 0.14.5 report is not presented as proof of a 0.15.1 producer regression. All 29 catalogs now state that the firmware update command/payload were not sent while warning the startup setting may have changed. The classifier retains payload or temporary-firmware uncertainty over a startup-setting label.

## Validation and limits

- Source inspected: `user_error.rs`, CLI parse/output, both optical `IssueKind` mappings, flash/recovery boundaries, Flash GUI worker/result paths, and Modify GUI operation/analysis paths. Nested cause-to-wrapper-to-render checks were added for the Pioneer startup-setting boundary and conflicting/stronger update evidence.
- Local validation on this follow-up branch: `cargo test -p freemkv-flash --lib` passed (687 passed, 18 ignored); `cargo test -p freemkv-flash-gui` passed (241 passed, 2 ignored); `cargo test -p freemkv-fw-gui` passed (10 passed); focused startup cause, contradictory wrapper, payload uncertainty, typed progress, and all-catalog issue tests passed.
- CI/QA for this follow-up is pending and must pass the documented dev → QA → main release workflow before any immutable release.
- No physical drive was exercised. `errors.unexpected` remains intentionally generic. Platform file-dialog and clap parser wording remains toolkit-owned. Translation parity and these author edits are not a substitute for native-speaker review.
