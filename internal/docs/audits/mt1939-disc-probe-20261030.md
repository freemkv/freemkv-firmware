# BH16NS48 failed-detection state capture

The detection-only format-1/5 BIN did not resolve the tester's failure. The next
deliverable uses that installed firmware's existing memory-read command and
requires no new flash. A hardware snapshot can distinguish an absent DI-ready
state, a classified-but-not-ready medium, an unexpected runtime setting, or a
native command rejection. It cannot retrospectively prove every stage reached.

`crates/freemkv-fw/examples/mt1939_disc_probe.rs` is a model-specific research
capture tool, built for x86-64 Windows. It discovers one BH16NS48 automatically,
verifies its INQUIRY product and three flash samples (hook, stub prefix and
state/flag/continuation bindings), then reads thirteen fixed SRAM windows.
It explicitly does not claim a whole-image hash verification. Wrong firmware
samples or a failed guard read prevent the source-bound SRAM capture.

The expected installed detection image hash is
`8a7ffc47910f7fef6abdac612f94f7d76d8f81149c704ae54e490a9aec1ff800`.
The probe reads the packed media state, native status/read-block byte, native
initialization status, DI-ready status, abort cells, native mode, DI buffer/base
offsets, availability, capacity end and runtime Unrestricted setting. It does
not dereference the selected DI buffer pointer. It then records vendor identity,
READ CAPACITY and GET CONFIGURATION responses. Standard media commands occur
after the SRAM snapshot to reduce disturbance of the captured state.

Every command result retains its CDB, allocation length, actual bytes or error,
and structured sense when available. A failed read decodes as null, never zero.
Snapshots containing memory failures are labeled partial. The reads have short
diagnostic timeouts and no automatic retry. State may still change between reads;
this is not an atomic capture or a history trace.

The tool issues no SET/RESET/SAVE, start/stop, sector read or firmware write.
Mock tests enforce the command allowlist, record wrong-image refusal before SRAM
reads, and verify error/null handling. The Windows executable is cross-compiled;
no real Windows optical drive is available in the development environment.

Build:

```sh
cargo test -p freemkv-fw --example mt1939_disc_probe
cargo clippy -p freemkv-fw --example mt1939_disc_probe -- -D warnings
CARGO_TARGET_X86_64_PC_WINDOWS_MSVC_RUSTFLAGS='-C target-feature=+crt-static' \
  cargo xwin build -p freemkv-fw --example mt1939_disc_probe \
  --target x86_64-pc-windows-msvc --release
```

The Desktop ZIP contains the executable, an administrator-run CMD launcher,
instructions and checksums. The tester should leave the same UHD inserted after
detection gives up, run the capture, and return the timestamped JSON beside the
executable. Capture errors also produce a JSON report. Existing detection BIN
and the locally prepared read-path BIN are not rebuilt by this step.
